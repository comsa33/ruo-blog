The storage and retrieval engine behind the memory service wasn't written here. It came from an open-source library. But as described in [the first post](/en/examples-beat-instructions), that library's extraction prompt had to be changed — Korean conversations were being extracted into English.

That's where the choice came in.

## Dependency, fork, or vendor

| Option              | Our changes | Upstream updates     | Diffability   |
| ------------------- | ----------- | -------------------- | ------------- |
| Use as a dependency | impossible  | automatic            | not needed    |
| Fork                | free        | cherry-pick required | blurs quickly |
| Vendor              | free        | selective            | maintainable  |

As a dependency the prompt can't be touched. As a fork it can, but within months nobody can tell whether a given line was always like that or something we did.

So I vendored it: pull the code into the repository wholesale, but keep it in a state where a diff against the original is always possible.

## The rules we kept

Staying diffable against the original meant following a few rules without exception.

No formatter touches it. Linters and import sorting all go in the exclude list, because formatting it even once makes it different code from the original and diffing stops working. If a commit hook objects, disable the hook and commit.

Every changed line carries a comment saying why. When comparing against upstream later, that comment is the only clue, and without it the next person just assumes the original was like that.

The import is split into three commits.

Follow this and you can always diff commit 1 against today to see everything we changed.

## What you learn from having to read it

You end up with no choice but to read someone else's code, and things that were invisible from the outside started showing up.

### A class that is async in name only

The library ships both a synchronous and an asynchronous class. I took it for granted that we should be using the async one.

Then I opened it.

It was doing the same thing we already do by handing sync code to a thread pool. The only difference is whether you hand over a whole request or one call at a time.

Switching would gain essentially nothing, and we'd have to maintain our changes twice. All eighteen modifications live on the sync path, so they'd have to be duplicated and kept in step.

The bottleneck was somewhere else.

### A feature with no switch

Version 2 of the library contains an undocumented entity linking feature. It extracts entities from memory sentences, embeds them into a separate table, and boosts memories sharing an entity at search time. A reasonable feature.

<Callout label="There is no switch" accent>
Nothing turns it on or off. It activates automatically if a morphological analysis library happens to be installed. It is dormant here only because that library is absent.

The moment somebody adds it as a dependency for a completely unrelated reason, an entity table appears and every ingest starts paying for entity embeddings — with no code change at all.

</Callout>

It's also close to useless for Korean. The model is hardcoded for English and a token counts as a name if its first character is uppercase, so Korean, which has no uppercase, never qualifies. Turned on, it costs and does nothing.

It could have been fixed by swapping the model and rewriting the capitalisation test and the English stopword filter, but that collides head-on with "keep our diff minimal". So I didn't fix it, and wrote down instead what turns it on and what happens when it does.

### Config keys that are silently ignored

Pass a wrong key name to the config object and it's simply ignored, with no error.

- Pass the database connection string under the key `dsn` and the key is ignored as wrong; there's no connection error, it quietly falls back to a default
- Point the history store at the wrong path and it drops to a local file database instead of PostgreSQL, with no log
- The graph config from v1 no longer exists in v2, but passing it is ignored without an error

All of these are the same kind of failure as in [the previous post](/en/failures-that-dont-throw): nothing throws.

## A delete path that isn't atomic

The delete path is not atomic. Removing the vector row, writing the history entry and cleaning up run in sequence on separate connections with no transaction. If the first commits and the rest fail, you get a memory that is gone with no record of its deletion.

Restructuring the vendored code to be atomic would blow up the diff, so we didn't, and put a compensating layer outside it instead. It backfills missing history and sweeps up rows left orphaned.

If the engine is replaced, the compensating layer goes with it. Until then, I judged that carrying this debt was better than tearing up the vendored code and losing the ability to diff against the original.
